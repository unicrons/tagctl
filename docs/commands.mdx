## Global Flags

These flags work with all commands:

| Flag | Short | Default | Description |
|------|-------|---------|-------------|
| `--config` | `-c` | `./tagctl.yaml` | Path to configuration file |
| `--output` | `-o` | `table` | Format printed on stdout, case-insensitive: `table`, `json` or `csv` for `scan`; `table` or `json` for `plan`, `diff`, `normalize`, `terraform` and `cost`; `json` for `evaluate`, which is also its default; `table` for the other commands. Any other value exits `2` |
| `--log-level` | `-l` | `error` | Log level: `error`, `info`, `debug`; an unknown value falls back to `info` with a warning |
| `--version` | - | - | Print the version and exit |
| `--help` | `-h` | - | Show help for command |

### Log Levels

| Level | Description |
|-------|-------------|
| `error` | Only show errors (default) |
| `info` | Show what each step is doing |
| `debug` | Show detailed trace for troubleshooting. All levels write to stderr, so stdout stays pipeable |

### Standard output

stdout carries only the output `--output` selects, so `tagctl scan -o json | jq`
and `tagctl scan -o csv > findings.csv` work without filtering. The banner,
spinners, the demo mode notice, the partial scan warnings of `scan`, `plan`,
`diff` and `--baseline`, the `apply` summary and confirmation prompt, and
notices about files written (`Detailed results saved to`, `Plan saved to`,
`Plan written to`, `Created tagctl.yaml`) go to stderr. `validate` prints its
warnings on stdout, since they are part of the report it was asked for.

## Exit codes

Every command exits with one of three codes, so a pipeline can tell a policy
that failed from a check that could not run:

| Code | Meaning |
|------|---------|
| `0` | Success, and every gate that was requested passed |
| `1` | A policy gate failed: `--fail-under` or `--fail-on-new` on `scan`, `evaluate` and `terraform`, `--fail-under` on `cost`, `diff --fail-on-regression`, `normalize --fail-on-drift` |
| `2` | Any other error: an unknown flag or wrong arguments, an `--output` format the command does not print, more than one report sent to `-`, an invalid config, an unreadable input or baseline file, `--fail-on-new` without `--baseline`, a [partial scan](#partial-scans) without `--allow-partial`, an `apply` with failed changes |

The reason is printed to stderr after `Error:`. An unknown command
(`tagctl nosuch`) exits `2`, but `tagctl help <topic>` with an unknown topic
prints the usage and exits `0`. Ctrl-C or SIGTERM makes `scan`, `apply` and
`cost` stop and exit `2`; any other command is ended by the signal itself.

## tagctl scan

Scan cloud resources and report tag compliance.

```bash
tagctl scan [flags]
```

<ParamField path="--region" type="string[]" default="all regions">
  AWS region(s) to scan; overrides `regions` in the config file. If omitted, all available regions are discovered and scanned. Also filters S3 buckets by their region.
</ParamField>

<ParamField path="--resource-type" type="string[]" default="every type">
  Only evaluate and report resource types matching this glob (`aws_s3_*`, `aws_instance`); repeat the flag to add more. The syntax is the one `ignore.resources` uses (Go `path.Match`: `*`, `?`, `[a-z]`), a comma is not a separator, and a malformed glob is rejected before anything is scanned. `ignore` rules still apply to what is left. See [Scanning some resource types](#scanning-some-resource-types)
</ParamField>

<ParamField path="--profile, -p" type="string">
  AWS profile from `~/.aws/config`; overrides `profile` in the config (which must have zero or one AWS entry)
</ParamField>

<ParamField path="--role" type="string">
  IAM role ARN to assume. `--external-id`, `--session-duration` (900–43200, default 3600), `--role-session-name` (default `tagctl`) and `--mfa-serial` (TOTP read from stdin) refine it
</ParamField>

<ParamField path="--verbose" type="boolean" default="false">
  Show all findings; by default the table stops after the first 10 (`... and N more findings`)
</ParamField>

<ParamField path="--mock" type="boolean" default="false">
  Use mock data for demonstration
</ParamField>

<ParamField path="--allow-partial" type="boolean" default="false">
  Succeed with a warning on stderr when discovery failed for part of the estate. Without it a [partial scan](#partial-scans) writes its reports and then fails
</ParamField>

<ParamField path="--output-dir" type="string" default="output">
  Directory the JSON, CSV and HTML reports are written to; created when missing. See [Output Files](#output-files)
</ParamField>

<ParamField path="--no-files" type="boolean" default="false">
  Write no JSON, CSV or HTML report. The stdout output and the [CI gate](#ci-gates) reports are unaffected. Cannot be combined with `--output-dir`
</ParamField>

```bash Another profile or an assumed role

tagctl scan --role arn:aws:iam::123456789012:role/TagctlScan --external-id 4f2c9a
```

```bash Verbose with debug logging
tagctl scan --verbose --log-level debug
```

```bash JSON output
tagctl scan --output json
```

```bash CSV export
tagctl scan --output csv > compliance.csv
```
</CodeGroup>

### Scanning some resource types

```bash
tagctl scan --resource-type 'aws_s3_*' --resource-type aws_instance
```

`--resource-type` filters the resources after discovery: every service is
still listed, then only the matching types are evaluated, counted and
reported. It narrows the reports and the gate, not the API calls or the scan
time (use `--region` for that), and a service that cannot be listed still
makes the scan [partial](#partial-scans) even when its types are filtered out.
Quote the glob so the shell does not expand it. When nothing matches, the scan
reports zero resources and warns on stderr. Demo mode (`--mock`) ignores the
flag with a warning, since its data is fixed.

### Output Files

Every scan generates reports in the `output/` directory, or in the one
`--output-dir` names. `--no-files` writes none of them.

| Format | File | Description |
|--------|------|-------------|
| JSON | `scan-TIMESTAMP.json` | Complete scan results with all metadata and findings |
| CSV | `scan-TIMESTAMP.csv` | All findings (PASS/FAILED) with resource ARNs |
| HTML | `scan-TIMESTAMP.html` | Standalone visual report: per-tag coverage, resource-type × tag matrix, accounts and a findings table with status filter and pager (25–250 rows or all). No external assets, opens offline; printing shows every row of the active filter |

Each finding includes:
- **Status**: `PASS` (tag present and valid) or `FAILED` (missing or invalid)
- **Resource ARN**: Full AWS ARN for the resource
- **Reason**: Why the finding was generated

<Tip>
The `--output` flag controls what's printed to stdout. Output files are generated regardless of it, unless `--no-files` is set. `tagctl diff` and `tagctl normalize` look for the latest scan in `output/`: with another `--output-dir`, pass them the scan files (`tagctl diff reports/scan-A.json reports/scan-B.json`, `tagctl normalize --scan reports/scan-A.json`).
</Tip>

`resources` is the inventory: one entry per evaluated resource, including those
no policy tag produced a finding for (an empty policy, or only optional tags the
resource does not carry). `identity` is the ARN when there is one, otherwise
`provider/account/region/id` with empty parts dropped; `diff` compares resources
by it. Scans written by older versions have no `resources` key.

`violations` and `violation_count` repeat the `FAILED` findings for tools that
read the older key. `by_tag` counts, per policy tag, the resources where the tag
is `present` or `missing`, and how many of the present ones are `invalid`. An optional tag only counts the resources
that carry it: its `missing` is always 0, its `compliance_percent` is the share
of those with a valid value, and it reports 100 when no resource carries it (the
HTML report shows that tag as not used).

### Partial scans

A scan is partial when discovery fails for part of the estate: a region or a
service the role cannot list, or one that keeps throttling after the retries.
The resources the other providers returned are still evaluated, and the JSON and
HTML reports carry the failures, one entry per provider that failed:

```json
{
  "scanned_at": "2026-02-02T10:51:48Z",
  "partial": true,
  "errors": [
    "provider aws: operation error EC2: DescribeInstances, api error UnauthorizedOperation"
  ],
  "total_resources": 142,
  ...
}
```

Both keys are omitted from a complete scan. The SARIF report marks a partial
scan in `runs[0].invocations[0]`: `executionSuccessful` is `false` and each
error is a `toolExecutionNotifications` entry. The CSV, JUnit and OCSF reports
are not marked.

Credentials are checked before discovery starts: an account whose credentials or
role are rejected at startup stops the scan with an error and no reports.

A partial scan writes every report, including `--sarif`, `--junit` and `--ocsf`,
and then fails with exit code `2` before the CI gate runs: a compliance
percentage over part of the estate can pass a gate the whole estate would fail.
`--allow-partial` accepts the
scan instead: a warning goes to stderr and the gate runs on the partial result.

`plan`, `diff` and `--baseline` print a warning to stderr when they read a
partial scan file. Resources it missed get no plan changes; in a diff they show
up as new or removed resources, and their failures as regressions or resolved.

## tagctl apply

Apply the planned tag changes.

```bash
tagctl apply [flags]
```

This is the only command that writes to the cloud. The shipped `TagctlScan`
role cannot run it; assume `TagctlApply` for this run with `--role` (see
[Scan role vs apply role](/credentials#scan-role-vs-apply-role)).

`apply` only adds and updates tags. A plan with any other action (for example
a hand-edited `remove`) is rejected when it is loaded, before the confirmation
prompt, and nothing is written. Interrupting a run (Ctrl-C) stops sending
changes: the ones not sent yet are reported as failed with `context canceled`.

<ParamField path="--plan" type="string" default="latest in --output-dir">
  Plan file to apply. If not specified, uses the most recent plan.
</ParamField>

<ParamField path="--output-dir" type="string" default="output">
  Directory the latest plan is looked up in
</ParamField>

<ParamField path="--profile, -p" type="string">
  AWS profile from `~/.aws/config`; overrides `profile` in the config (which must have zero or one AWS entry)
</ParamField>

<ParamField path="--role" type="string">
  IAM role ARN to assume. `--external-id`, `--session-duration` (900–43200, default 3600), `--role-session-name` (default `tagctl`) and `--mfa-serial` (TOTP read from stdin) refine it
</ParamField>

<ParamField path="--auto-approve" type="boolean" default="false">
  Skip confirmation prompt
</ParamField>

<ParamField path="--mock" type="boolean" default="false">
  Simulate the apply without calling any cloud API. Also used automatically when the config has no cloud provider
</ParamField>

<CodeGroup>
```bash Interactive apply (uses latest plan)
tagctl apply
```

```bash Apply specific plan
tagctl apply --plan output/plan-20260202-143052.json
```

```bash Auto-approve (CI/CD)
tagctl apply --auto-approve
```

```bash Full workflow
tagctl scan
tagctl plan
tagctl apply
```
</CodeGroup>

## tagctl evaluate

Evaluate resources from external JSON input against the tag policy. This command is designed for integration with tools like [Prowler](https://github.com/prowler-cloud/prowler).

```bash
tagctl evaluate [flags]
```

<ParamField path="--resources" type="string" default="-">
  Path to JSON file with resources, or `-` for stdin
</ParamField>

<ParamField path="--policy" type="string" default="auto-discover">
  Path to tagctl.yaml policy file. If not specified, auto-discovers from current directory.
</ParamField>

<CodeGroup>
```bash Evaluate from file
tagctl evaluate --resources resources.json
```

```bash Evaluate from stdin
cat resources.json | tagctl evaluate
```

```bash With specific policy
tagctl evaluate --resources resources.json --policy custom.yaml
```

The policy must define at least one required or optional tag. A `--policy` file
is decoded and validated the same way as the auto-discovered `tagctl.yaml`.

```bash Filter failed findings with jq
tagctl evaluate --resources resources.json | jq '.findings[] | select(.status == "FAILED")'
```
</CodeGroup>

### Input Format

Resources must be provided as a JSON array:

```json
[
  {
    "id": "i-0abc123def456",
    "arn": "arn:aws:ec2:us-east-1:123456789:instance/i-0abc123def456",
    "type": "aws_instance",
    "name": "web-prod-api-1",
    "region": "us-east-1",
    "account": "123456789",
    "provider": "aws",
    "tags": {
      "environment": "prod",
      "team": "backend"
    }
  }
]
```

| Field | Required | Description |
|-------|----------|-------------|
| `id` | Yes | Resource identifier |
| `arn` | No | AWS ARN (optional) |
| `type` | Yes | Resource type (e.g., `aws_instance`, `aws_s3_bucket`) |
| `name` | No | Human-readable name |
| `region` | No | Cloud region |
| `account` | No | Cloud account ID |
| `provider` | No | Cloud provider (`aws`, `gcp`, `azure`) |
| `tags` | Yes | Map of tag key-value pairs |

### Output Format

The command prints JSON with findings and summary; `json` is the only `--output`
format it accepts. A report sent to stdout with `--sarif -`, `--junit -` or
`--ocsf -` takes its place.

```json
{
  "findings": [
    {
      "resource": {
        "id": "i-0abc123def456",
        "type": "aws_instance",
        "name": "web-prod-api-1"
      },
      "tag": "cost-center",
      "status": "FAILED",
      "reason": "missing"
    },
    {
      "resource": {
        "id": "i-0abc123def456",
        "type": "aws_instance",
        "name": "web-prod-api-1"
      },
      "tag": "environment",
      "status": "PASS",
      "reason": "compliant",
      "actual": "prod"
    }
  ],
  "summary": {
    "total_resources": 1,
    "total_findings": 2,
    "passed": 1,
    "failed": 1
  }
}
```

### Finding Status

| Status | Description |
|--------|-------------|
| `PASS` | Tag is present and valid |
| `FAILED` | Tag is missing or invalid |

### Finding Reasons

| Reason | Description |
|--------|-------------|
| `compliant` | Tag present with valid value |
| `missing` | Required tag not present |
| `invalid_value` | Tag value not in allowed list |
| `invalid_format` | Tag value doesn't match pattern |

## tagctl diff

Compares two scans and reports what moved between them.

A compliance percentage on its own says little: `62%` is a crisis if last week
was `88%`, and a triumph if last week was `40%`. `diff` reports the drift, which
is both the number teams act on and the one a pipeline can be gated on.

```bash
# Compare the two most recent scans in output/
tagctl diff

# Compare two specific scans
tagctl diff output/scan-20260101-120000.json output/scan-20260201-120000.json

# Treat one file as the baseline and compare it against the latest scan
tagctl diff baseline.json

# Machine-readable
tagctl diff -o json
```

### Flags

| Flag | Description |
|------|-------------|
| `--fail-on-regression` | Exit `1` if any finding regressed |

### What counts as drift

A finding is identified by the resource it belongs to **plus** the tag it
checks, so one resource failing two tags is two findings that move
independently.

| Category | Meaning |
|----------|---------|
| **Regressed** | Fails now, did not fail in the baseline |
| **Resolved** | Failed in the baseline, does not fail now |
| **Still failing** | Failed in both scans |
| **New resources** | Present only in the current scan |
| **Removed resources** | Present only in the baseline scan |

A resource with the same ID in a different account or region is a different
resource.

New and removed resources come from each scan's `resources` inventory plus the
resources its findings name, so a resource with no findings still counts. A scan
written by an older version has no inventory and only names the resources in its
findings. When such a file counts resources but has no findings either (an empty
policy), `diff` prints a warning to stderr: new and removed resources may be
wrong. Regressions and resolved findings are not affected.

When either file is a [partial scan](#partial-scans), `diff` prints a warning to
stderr: resources discovery missed look new or removed, and their findings look
regressed or resolved.

Older versions counted every resource without an optional tag as `missing`.
Comparing a scan written by one of them with a newer scan shows a one-off jump
in that tag's row under **By tag**; findings and required tags compare as before.

### Example output

```
Baseline: output/scan-20260101-100000.json (2026-01-01 10:00:00)
Current:  output/scan-20260201-100000.json (2026-02-01 10:00:00)

Compliance: 88.0% → 62.0% (-26.0%)

Regressed: 2    Resolved: 1    Still failing: 0
New resources: 1    Removed resources: 1

Regressions:
  ✗ aws_instance i-1 (111) — required tag 'owner' is missing
  ✗ aws_lb i-9 (111) — required tag 'owner' is missing

Resolved:
  ✓ aws_instance i-2 (111) — tag 'owner' is now compliant

By tag:
  owner                     88.0% →  62.0%  (-26.0%)
```

### Gating a pipeline on drift

Adopting tagctl on an estate that is already non-compliant does not have to turn
the build red on day one. Gate on the *change* instead of the absolute number:

```bash
tagctl scan
tagctl diff baseline-scan.json --fail-on-regression
```

The build fails only when something got worse than the committed baseline.

## tagctl cost

Joins your tag policy with AWS Cost Explorer and answers the question that gets
tagging work funded: **how much of this bill cannot be attributed to anyone?**

Cost allocation tags are not retroactive. Spend that landed on an untagged
resource can never be assigned to a team, however diligently you tag afterwards.
The number this reports is a permanent loss, not a backlog item — which is why
it argues for the work in a way a compliance percentage never does.

```bash
# The last 30 days, for the tags your policy requires
tagctl cost

# A specific window
tagctl cost --days 90

# Specific tags, whatever the policy says
tagctl cost --tag owner --tag cost-center

# Fail when attribution is too low
tagctl cost --fail-under 80
```

### Flags

| Flag | Description |
|------|-------------|
| `--days <n>` | How many days back to report on (default `30`, minimum `1`) |
| `--tag <tag>` | Tag to report on (repeatable; defaults to the policy's required tags) |
| `--fail-under <pct>` | Exit `1` if any tag accounts for less than this share of spend |
| `--profile <name>`, `-p` | AWS profile (defaults to the first configured account). Cost Explorer is always called through `us-east-1` |
| `--role <arn>` | IAM role to assume; `--external-id`, `--session-duration`, `--role-session-name` and `--mfa-serial` refine it |
| `--output json` | Machine-readable report instead of the table |

### Activate your cost allocation tags first

<Warning>
  Cost Explorer only groups by a tag once it has been **activated as a cost
  allocation tag** in the Billing console, under *Cost allocation tags*. A tag
  that has never been activated reports as accounting for nothing at all, which
  looks identical to nothing being tagged.

  Activation is also not retroactive: it applies from the month you enable it.
</Warning>

### IAM permissions

`cost` needs one action the other commands do not, `ce:GetCostAndUsage`.
The `TagctlScan` role and the scan policy already include it; a role of your
own needs:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ce:GetCostAndUsage"],
      "Resource": "*"
    }
  ]
}
```

Cost Explorer is a global service reached through `us-east-1`, and it reports
for the whole payer account, so a single profile is enough regardless of how
many accounts you scan.

<Note>
  Cost Explorer charges per paginated API request. `cost` makes one request per
  tag per page of results, so a report over a handful of tags costs cents, not
  dollars.
</Note>

### Example output

```
Period: 2026-01-08 to 2026-02-07 (30 days)
Total spend: 184320.55 USD

  cost-center
      attributed:      36864.11 USD  (20.0%)
      unattributed:   147456.44 USD  (80.0%)
      top values:
        cc-platform                      21033.20 USD
        cc-data                          15830.91 USD

  owner
      attributed:     165888.50 USD  (90.0%)
      unattributed:    18432.05 USD  (10.0%)
      top values:
        platform@example.com             98221.33 USD
        data@example.com                 67667.17 USD

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Tags are listed worst-attributed first, because that is the one worth fixing.

### How the numbers are derived

Cost Explorer groups spend by tag key and returns one group per value, plus a
group with an **empty value** covering everything that does not carry the tag.
That empty group is the unattributed figure.

Every tag is measured over the same total spend, so the totals are not summed
across tags: `owner` at 90% and `cost-center` at 20% describe the same bill from
two angles.

## tagctl terraform

Evaluates the tags in a Terraform plan or state file against the same policy
the live scan uses, before anything is created.

Cost allocation tags are not retroactive. A resource that runs untagged for two
weeks has two weeks of spend that can never be attributed to anyone. Catching a
missing tag in a pull request costs nothing.

```bash
# The usual pattern
terraform plan -out=tfplan
terraform show -json tfplan | tagctl terraform

# Or from a file
terraform show -json tfplan > plan.json
tagctl terraform --plan plan.json

# Only what this change creates or updates
tagctl terraform --plan plan.json --changed-only

# Check what is already deployed
terraform show -json > state.json
tagctl terraform --state state.json
```

### Flags

| Flag | Description |
|------|-------------|
| `--plan <file>` | `terraform show -json` output for a plan (`-` for stdin, the default) |
| `--state <file>` | `terraform show -json` output for a state file |
| `--changed-only` | Only evaluate resources the plan creates or updates; rejected together with `--state` |
| `--output json` | Machine-readable findings instead of the table |

`--plan` and `--state` are mutually exclusive.

All the [CI gate flags](#ci-gates) work here too, so a plan can fail a pull
request and annotate it with SARIF.

### What gets evaluated

| Input | Evaluated |
|-------|-----------|
| Managed resources with a tag attribute | Yes |
| Data sources | No — read-only lookups cannot be tagged |
| Types with no tag attribute (an IAM policy, say) | No — flagging them would be noise |
| A resource whose tags are unset (`"tags": null`) | Yes, reported as untagged |
| A tag whose value is only known after apply | Yes, the key counts as present and passes without checking `values` or `pattern`; it is listed in the resource's `unknown_tags` and named on stderr |
| A resource whose whole tag map is only known after apply | No — skipped with an error on stderr naming it, since its tags cannot be read yet |
| With `--changed-only`: create and update | Yes |
| With `--changed-only`: delete and no-op | No — a resource being destroyed needs no tags, and a no-op is already live |

Child modules are walked recursively, up to 100 levels deep. Only
`format_version` 1.x of the `terraform show -json` output is read; a document
in another major version is rejected rather than misread.

### default_tags are respected

Tags are read from `tags_all` when Terraform provides it, which is the set that
includes the AWS provider's `default_tags`. Reading `tags` alone would report a
violation on every resource the provider tags for you:

```hcl
provider "aws" {
  default_tags {
    tags = {
      owner       = "team@example.com"
      environment = "prod"
    }
  }
}
```

When `tags_all` is null (a state written before the provider had the
attribute) or only known after apply (a tag value that references a resource
not created yet), `tags` is read instead. For that resource `default_tags` are
not counted, so a tag the provider would add can show as missing.

The Google and Kubernetes providers use `labels`, which is read the same way.

### Example output

```
Source: plan.json (resources being created or updated)
Checked 2 resources against the tag policy

1 of 2 resources would be non-compliant (50.0% compliant):

  aws_s3_bucket.logs
      ✗ required tag 'owner' is missing
      ✗ required tag 'environment' is missing

Fix the tags in your Terraform, or set them with the provider's default_tags.
```

Resources are grouped by Terraform address, which is what the author has to go
and edit.

### Blocking a pull request

```yaml
- name: Check tags on the plan
  run: |
    terraform show -json tfplan > plan.json
    tagctl terraform --plan plan.json --changed-only \
      --fail-under 100 --sarif tagctl.sarif
```

`--changed-only --fail-under 100` is the useful combination for a pull request:
everything this change touches must be fully compliant, without holding the
author responsible for the rest of the estate.

## tagctl normalize

Finds tag values that mean the same thing but are spelled differently, and
proposes one canonical spelling for each group.

`prod`, `Production`, `PROD` and `production` are four different strings to
every cost report that groups by that tag, so one inconsistency across a large
fleet silently splits your spend across four buckets. A missing-tag check never
catches this: every one of those resources *is* tagged.

```bash
# Report drift in the most recent scan
tagctl normalize

# Read from a specific scan or resource file
tagctl normalize --scan output/scan-20260201-120000.json
tagctl normalize --resources resources.json

# Write a remediation plan, then apply it
tagctl normalize --out output/normalize-plan.json
tagctl apply --plan output/normalize-plan.json

# Fail a pipeline when drift appears
tagctl normalize --fail-on-drift
```

### Flags

| Flag | Description |
|------|-------------|
| `--scan <file>` | Scan file to read resources from (default: most recent scan) |
| `--resources <file>` | Resource JSON, as accepted by `tagctl evaluate`; mutually exclusive with `--scan` |
| `--max-distance <n>` | Edit distance for typo matching; `0` disables it, negative values are rejected (default `1`) |
| `--abbreviations` | Group a value with a longer one it is a prefix of (default `true`) |
| `--ignore-tag <tag>` | Tag key to leave alone (repeatable) |
| `--out <file>` | Write a remediation plan to this path |
| `--fail-on-drift` | Exit `1` if any drift is found |
| `--output json` | Machine-readable report instead of the table |

Values listed under `policy.optional[].values` count as canonical spellings, the same as `policy.required[].values`.

### How values are grouped

Three signals, in decreasing order of confidence:

| Signal | Matches | Example |
|--------|---------|---------|
| `casing` | Differ only in case, separators or spacing | `team-platform` / `Team_Platform` / `team platform` |
| `typo` | Within `--max-distance` edits of each other, and no more than one edit per 3 letters or digits of the shorter value; the longer value needs at least 4 | `staging` / `stagng`, `prod` / `prd` |
| `abbreviation` | One is a prefix of the other, at least 3 characters | `prod` / `production` |

Groups are formed by chaining matches, so a value can join a group through
another variant without matching the canonical spelling itself. With
`--max-distance 1`, `stagn` is one edit from `stagng` and two from
`staging`. Such a value is reported with the match `transitive`: it is shown
for review, but `--out` leaves it out of the plan and it is not counted in
"affecting N resource(s)".

### Safety rules

These are what keep the proposals trustworthy:

- **A value your policy allows is never rewritten**, and is preferred as the
  canonical spelling even when a different spelling is more common.
- **Two values the policy both allows are never collapsed into each other.**
  Without this, `dev` and `devops` would be merged, which would be wrong.
- **Values that differ in a digit are never typos or abbreviations.**
  `us-east-1` / `us-east-2` and `build-10` / `build-100` stay apart. A typo in
  the letters still counts: `backend-1` / `backnd-1`.
- **Short values need a closer match.** `us` / `uk`, `api` / `app` and, at
  `--max-distance 2`, `test` / `temp` are not typos of each other, while
  `prod` / `prd` is.
- **The `Name` tag is always skipped.** Its values are unique by design, so
  clustering it would propose renaming half the estate.
- **Nothing is written.** `normalize` reports, and optionally emits a plan you
  review before running `apply`.

### Known limits

Values one letter apart are grouped once they are long enough, even when they
mean different things: `team-a` / `team-b` and `data` / `date` are reported as
typos. Review each cluster before applying a plan. To keep such values apart,
list both in the tag's policy `values` (two allowed values are never collapsed),
or skip the tag with `ignore_tags` or `--ignore-tag`.

### Choosing the canonical value

1. A value the policy allows, if the group contains one.
2. Otherwise the most common spelling.
3. Ties break case-insensitively by name, then in favour of the plainer,
   lower-case form, so a tie never leaves a shouted value as canonical.

### Example output

```
Source: resources.json
Scanned 29 resources across 2 tag(s)

Found 3 cluster(s) of inconsistent values, affecting 16 resource(s):

  environment → "production"  (allowed by policy, 12 resources)
      "Production"               5 resources [casing]
      "PROD"                     3 resources [abbreviation]
      "prod"                     2 resources [abbreviation]

  environment → "staging"  (allowed by policy, 6 resources)
      "stagng"                   1 resource  [typo]

  team → "platform"  (most common, 22 resources)
      "Platform"                 5 resources [casing]
```

### JSON output

`--output json` prints the same clusters. Each variant's `match` is `casing`,
`typo`, `abbreviation` or `transitive`, as described above:

```json
{
  "clusters": [
    {
      "tag": "environment",
      "canonical": "staging",
      "canonical_count": 5,
      "canonical_from_policy": false,
      "variants": [
        { "value": "stagng", "count": 2, "match": "typo", "resources": [] },
        { "value": "stagn", "count": 1, "match": "transitive", "resources": [] }
      ]
    }
  ],
  "resources_scanned": 8,
  "tags_scanned": 1
}
```

`resources` lists the full resource objects carrying each variant; it is
shortened to `[]` here.

### Configuration

```yaml
normalize:
  max_distance: 2             # edit distance for typos (default 1, 0 disables)
  match_abbreviations: true   # group prod with production (default true)
  ignore_tags:                # on top of Name, always ignored
    - build-id
    - commit-sha
```

Flags override the config file.

## CI gates

`scan`, `evaluate` and `terraform` accept the same set of gate flags, which turn tagctl
from a report into a build step.

### Flags

| Flag | Description |
|------|-------------|
| `--fail-under <pct>` | Exit `1` if compliance is below this percentage |
| `--fail-on-new` | Exit `1` if any finding regressed against `--baseline` |
| `--baseline <file>` | Baseline scan `--fail-on-new` compares against |
| `--sarif <path>` | Also write findings as SARIF (`-` for stdout) |
| `--junit <path>` | Also write findings as JUnit XML (`-` for stdout) |
| `--ocsf <path>` | Also write findings as OCSF Compliance Finding events (`-` for stdout) |

Reports are written **before** the gate runs, so a failing build still uploads
its findings. Report files are created readable only by the current user
(`0600`), like the files in `output/`: they carry every tag value and ARN.

A report written to `-` replaces the command's own stdout output (the table, or
the JSON `evaluate` prints), so stdout holds a single document. Sending more
than one report to `-`, or combining one with an explicit `--output`, is a usage
error and exits `2`.

### Choosing a gate

The two checks answer different questions.

`--fail-under` is an absolute bar: *this estate must be at least this
compliant*. Use it once you are near the target.

`--fail-on-new` is relative: *whatever state we are in, do not make it worse*.
This is what lets a team adopt tagctl on a large non-compliant estate without
turning the build red for months.

```bash
# Absolute bar
tagctl scan --fail-under 90

# Do not regress against a committed baseline
tagctl scan --fail-on-new --baseline baseline-scan.json

# Both
tagctl scan --fail-under 75 --fail-on-new --baseline baseline-scan.json
```

Without a `--baseline`, `--fail-on-new` is a usage error rather than a silent
pass: there is nothing to compare against, and quietly passing would hide a
regression.

### SARIF

SARIF 2.1.0 output uploads straight into GitHub code scanning, so violations
appear in the Security tab and as pull request annotations.

- One **rule per tag**, so alerts group by the tag that failed.
- A **missing** required tag is `error`; an invalid value is `warning`. A
  resource with no owner tag cannot be attributed at all, while one with a
  misspelt value is at least identifiable.
- Only failures are emitted. A SARIF result means "look at this".
- Each result carries a **partial fingerprint** of the resource and tag, so
  GitHub keeps an alert attached across scans instead of closing and reopening
  it every run.
- `runs[0].automationDetails.id` is `tagctl/scan/`, `tagctl/evaluate/` or
  `tagctl/terraform/`. Code scanning uses it as the category, so uploads from
  different commands do not close each other's alerts.
- `runs[0].invocations[0].executionSuccessful` is `false` for a
  [partial scan](#partial-scans), with each discovery error as a
  `toolExecutionNotifications` entry, and `true` otherwise.

Cloud resources have no source file, so results are anchored to the config file
the command read: `--config`, the discovered `tagctl.yaml`, or `evaluate
--policy`. The path is relative to the working directory, with forward slashes,
so run tagctl from the repository root for GitHub to link the file. Without a
config file the anchor is `tagctl.yaml`. Each result also carries the resource
identity as a SARIF *logical location*.

### JUnit

JUnit XML is understood by essentially every CI system.

- Cases are grouped into **one suite per tag**, which makes it obvious when
  every failure is the same tag.
- **Passing findings are included**, so the reported ratio is truthful rather
  than a wall of failures with no denominator.
- Each failure body carries the resource, type, account, region, expected and
  actual values, and the ARN, so it can be acted on without opening the scan.
- The `classname` is `provider.account.region`, leaving out the parts a
  resource does not have: a Terraform plan gives `aws`.

### OCSF

`--ocsf` writes every finding as an [OCSF](https://schema.ocsf.io) 1.4
**Compliance Finding** event (`class_uid` 2003), the class the schema defines
for "results of evaluations performed against resources to check compliance
with a standard", which is exactly what a tag policy check is.

- **Passing findings are included** with `compliance.status` `Pass`, for the
  same reason JUnit includes them: a consumer needs the denominator.
- `finding_info.uid` is the same `resource#tag` identity SARIF uses as its
  fingerprint, so a SARIF alert and an OCSF event for the same problem share
  an id.
- The policy rule travels in `compliance.requirements`; the tag name is the
  `compliance.control`.

The full field mapping, an example event and ingestion notes are in
[OCSF output](/integrations/ocsf).

### GitHub Actions

```yaml
name: Tag compliance

on:
  schedule:
    - cron: '0 6 * * 1'
  pull_request:

permissions:
  contents: read
  security-events: write   # required to upload SARIF

jobs:
  tag-compliance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}   # the TagctlScan role
          aws-region: us-east-1

      - name: Install tagctl
        run: go install github.com/unicrons/tagctl/cmd/tagctl@latest

      - name: Scan
        run: |
          tagctl scan \
            --sarif tagctl.sarif \
            --junit tagctl-junit.xml \
            --ocsf tagctl.ocsf.json \
            --fail-on-new --baseline .tagctl/baseline-scan.json

      # Runs even when the gate failed, so findings are always visible.
      - name: Upload SARIF
        if: always()
        uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: tagctl.sarif

      - name: Publish test report
        if: always()
        uses: mikepenz/action-junit-report@v4
        with:
          report_paths: tagctl-junit.xml
```

Commit `.tagctl/baseline-scan.json` and refresh it whenever you deliberately
accept the current state. Every regression after that fails the build.

### Exit codes

| Code | Meaning |
|------|---------|
| `0` | The gate passed, or no gate was requested |
| `1` | The gate failed |
| `2` | The gate could not be evaluated: bad flags, an invalid config, an unreadable input or baseline, or a partial scan without `--allow-partial` |

A step that must not treat a broken run as a policy failure, or the other way
round, can branch on the code; see [Exit codes](#exit-codes).

The reason is printed to stderr:

```
Error: compliance gate failed: compliance is 33.3%, below the required 80.0%
```
