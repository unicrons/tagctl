tagctl can automatically fix tags using four types of rules:

<CardGroup cols={2}>
  <Card title="Rename" icon="right-left">

  <Card title="Inference" icon="magnifying-glass">

  </Card>
  <Card title="Inheritance" icon="sitemap">
    Copy tags from the parent resource
  </Card>
  <Card title="Defaults" icon="shield">
    Apply fallback values
  </Card>
</CardGroup>

Rules are applied in this order during `tagctl plan`.

## Rename Rules

Rename rules fix a tag that has the right value under the wrong key: `Env`
instead of `environment`, `CostCentre` instead of `cost-center`.

### How It Works

```
Resource: web-1, tags Env = "prod"
           ↓
Rename rule: Env → environment
           ↓
Plan:  + environment = "prod"   (renamed: renamed from 'Env')
       - Env = "prod"           (renamed: renamed to 'environment')
```

### Configuration

```yaml
rules:
  rename:
    - from: Env
      to: environment

    - from: env
      to: environment

    # Only on some resource types
    - resource: "aws_s3_*"
      from: CostCentre
      to: cost-center
```

| Field | Meaning |
|-------|---------|
| `from` | Tag key to remove. Required, case-sensitive |
| `to` | Tag key that receives the value. Required, different from `from` |
| `resource` | Optional glob for the resource types the rule applies to (same syntax as [Resource Patterns](#resource-patterns)). Defaults to every type |

Rename rules run on every resource in the scan that carries `from`, whether or
not the resource has a failed finding, and before the other rules: a tag a
rename sets is not inferred, inherited or defaulted as well.

| Resource carries | Plan |
|------------------|------|
| `from` only | Add `to` with the value, remove `from` |
| `from` and `to` with the same value | Remove `from` |
| `from` and `to` with different values | **Conflict**: nothing is planned, both tags stay |

### Conflicts

A rename never overwrites. When the target key already holds another value,
or two rules would write different values into it, the plan leaves the
resource alone and reports the conflict after its summary:

```
Conflicts: 1 rename(s) skipped, the target tag holds another value
  ! aws_instance (web-1): cannot rename 'Env' to 'environment': 'environment' is already 'dev', not 'prod'
```

The same list is in the plan JSON under `conflicts`. Decide which value is
right, fix the tag by hand and plan again. A conflicting `from` key is kept
even when `policy.forbidden` forbids it, so its value is not lost.

The value is moved as is. If it does not satisfy the policy of the new key
(`production` where `prod` is required), the next scan reports it as
`invalid_value`; use [`from_tag`](#from-another-tag) with a `values` map when
the values need translating too.

Chains are rejected when the config loads: with `Env → env` and
`env → environment`, write `Env → environment` instead.

## Removing Tags

Two things make `tagctl plan` propose a removal (`-` in the plan):

- a rename rule, for the old key;
- a tag [`policy.forbidden`](/configuration#forbidden-tags) forbids, with the
  reason `forbidden`. No rule is needed: forbidding a tag is asking for it to
  go.

The plan only proposes. `tagctl apply` skips every removal unless it is run
with `--allow-removals`: by default a rename adds the new key and keeps the
old one, and a forbidden tag stays where it is. The skipped removals are
reported, not counted as failures.

```bash
tagctl apply                    # additions and updates only
tagctl apply --allow-removals   # also removes the tags the plan removes
```

<Warning>
  Removing a tag cannot be undone from the plan: the plan file keeps the old
  value (`old_value`), tagctl does not put it back. With `--allow-removals`
  `tagctl apply` lists the removals before asking for confirmation. The
  shipped apply role also needs `AllowTagRemoval=true`
  ([Tag Removal](/providers/aws#tag-removal-opt-in)) to remove a tag.
</Warning>

A forbidden value on a required tag (`environment: test`) is removed like any
other forbidden tag, which leaves the tag missing: the next scan reports it
and the next plan fills it from your inference, inheritance or default rules.

## Inference Rules

Inference rules extract tag values from resource naming conventions.

### How It Works

```
Resource name: "web-prod-api-server-1"
                     ↓
Pattern match: "-prod-" found
                     ↓
Tag applied: environment = "prod"
```

### Configuration

```yaml
rules:
  infer:
    - tag: environment
      from_name:
        - pattern: "-prod-|-production-"
          value: prod
        - pattern: "-staging-|-stg-"
          value: staging
        - pattern: "-dev-|-development-"
          value: dev

    - tag: team
      from_name:
        - pattern: "^web-|^frontend-"
          value: frontend
        - pattern: "^api-|^backend-"
          value: backend
```

### Pattern Syntax

Patterns use Go regular expressions:

| Pattern | Matches |
|---------|---------|
| `-prod-` | Contains "-prod-" |
| `^web-` | Starts with "web-" |
| `-api$` | Ends with "-api" |
| `-prod-\|-production-` | Contains either |
| `-(dev\|stg\|prod)-` | Contains -dev-, -stg-, or -prod- |

<Tip>
  Patterns are evaluated in order—first match wins. Put more specific patterns first.
</Tip>

### Example

Given this configuration:

```yaml
rules:
  infer:
    - tag: environment
      from_name:
        - pattern: "-prod-"
          value: prod
        - pattern: "-dev-"
          value: dev
```

| Resource Name | Inferred Tag |
|--------------|--------------|
| `web-prod-api-1` | `environment: prod` |
| `db-dev-postgres` | `environment: dev` |
| `cache-redis-main` | *(no match)* |

### From Another Tag

`from_tag` takes the value from another tag on the same resource, which is
how a legacy key (`env`, `Environment`) feeds the one the policy requires:

```yaml
rules:
  infer:
    - tag: environment
      from_tag:
        # Translate the values that differ; anything else infers nothing
        - tag: env
          values:
            production: prod
            development: dev
        # No values: copy the value as is
        - tag: Environment
      from_name:
        - pattern: "-prod-"
          value: prod
```

| Field | Meaning |
|-------|---------|
| `tag` | Tag key to read. Required, case-sensitive, and different from the tag being inferred |
| `values` | Optional map from the source value to the value to set. Without it the value is copied unchanged; with it a value missing from the map is skipped |

Sources are tried in order and the first usable one wins. A resource that
does not carry the source tag, carries it empty, or carries a value outside
`values` falls through to the next source and then to `from_name`: a tag
already on the resource is a stronger signal than its name. The change is
reported as `inferred` with the source `from tag '<key>'`, and the source tag
is left in place.

## Inheritance Rules

Inheritance rules copy a missing tag from the resource a resource hangs
from: a volume from the instance it is attached to, a snapshot from its
source volume.

### How It Works

```
Resource: vol-0abc (no environment tag), attached to i-0123
           ↓
Parent: i-0123 has environment = "prod"
           ↓
Tag applied: environment = "prod"   (inherited: from attached instance i-0123)
```

### Configuration

```yaml
rules:
  inherit:
    - resource: aws_ebs_volume
      from: attached_instance
      tags: [environment, cost-center, owner]

    # Snapshots take theirs from the volume they were made from
    - resource: aws_ebs_snapshot
      from: source_volume
      tags: [environment, owner]

    # No from: follow whichever parent the scan recorded
    - resource: "aws_*"
      tags: [cost-center]
```

| Field | Meaning |
|-------|---------|
| `resource` | Glob for the resource types the rule applies to (same syntax as [Resource Patterns](#resource-patterns)). Required |
| `from` | Relation to follow, from the table below. Optional: without it every parent recorded for the resource is tried, in alphabetical order of relation |
| `tags` | Tags to copy. Required, at least one |

### Supported Relations

The scan records the parent while it lists each resource, from fields the
list call already returns, so inheritance costs no extra API calls.

| `from` | Resource type | Parent |
|--------|---------------|--------|
| `attached_instance` | `aws_ebs_volume` | The instance it is attached to. Not recorded for a volume attached to several instances |
| `attached_instance` | `aws_eip` | The instance the address is associated with |
| `source_volume` | `aws_ebs_snapshot` | The volume it was created from |
| `vpc` | `aws_instance`, `aws_subnet`, `aws_security_group`, `aws_nat_gateway`, `aws_vpc_endpoint` | The VPC it lives in |
| `vpc` | `aws_internet_gateway` | The VPC it is attached to |

Any other `from` value is rejected when the config loads.

### What Gets Inherited

- Only tags the resource is **missing** and the rule lists. An existing tag is
  never overwritten.
- The parent must be in the same scan. A parent that was deleted (the source
  volume of an old snapshot), that sits in an ignored resource type or that
  the scan missed hands down nothing.
- A parent value that fails the policy is not copied: inheritance never
  spreads an invalid value.
- A parent that lacks the tag hands down what it would inherit itself, so a
  snapshot reaches the instance through its volume (up to 8 levels).
- The change is a normal `add` with reason `inherited` and the parent in its
  source, for example `from attached instance i-0123`.

<Warning>
  Parents are recorded in the scan file. A scan written before tagctl recorded
  them has none: `plan` then warns that `rules.inherit` could not be applied
  instead of producing an empty plan silently. Run `tagctl scan` again.
</Warning>

## Default Rules

Default rules apply fallback values when tags are missing. Use as a safety net.

### How It Works

```
Resource: legacy-bucket (no owner tag)
           ↓
Default rule: when owner absent, set owner
           ↓
Tag applied: owner = "platform-team@company.com"
```

### Configuration

```yaml
rules:
  defaults:
    # Global default for missing owner
    - resource: "*"
      when:
        tag:owner: absent
      set:
        owner: platform-team@company.com
        needs-review: "true"

    # Specific defaults for S3 buckets
    - resource: "aws_s3_bucket"
      when:
        tag:data-classification: absent
      set:
        data-classification: internal

    # Defaults for untagged EC2 instances
    - resource: "aws_instance"
      when:
        tag:environment: absent
      set:
        environment: unknown
        requires-classification: "true"
```

### Resource Patterns

| Pattern | Matches |
|---------|---------|
| `*` | All resources |
| `aws_*` | All AWS resources |
| `aws_instance` | Only EC2 instances |
| `aws_s3_*` | S3 buckets and related |
| `aws_*_group` | Security groups, log groups, Auto Scaling groups... |
| `k8s_*` | All Kubernetes resources (values must be [valid label values](/providers/kubernetes#limits)) |

Patterns use Go `path.Match` syntax (`*`, `?`, `[...]`); a malformed one is
rejected when the config loads.

### Conditions

Every condition under `when` must hold for the rule to apply. Tag names are
case-sensitive.

| Condition | Meaning |
|-----------|---------|
| `tag:NAME: absent` | Tag is not present |
| `tag:NAME: VALUE` | Tag is present with exactly `VALUE` |

A key without the `tag:` prefix and an empty value are rejected when the config
loads. `present` is reserved for a future condition and rejected as well, so a
tag whose literal value is `present` cannot be matched.

<Note>
  More conditions like `tag:NAME: present` and `created_before` are planned for future releases.
</Note>

## Rule Priority

When multiple rules could apply:

```
1. Existing tags (never overwritten)
        ↓
2. Rename rules (value moved from another key)
        ↓
3. Inference rules (from another tag, then from the resource name)
        ↓
4. Inheritance rules (from the parent resource)
        ↓
5. Default rules (fallback values)
```

### Example Flow

Resource: `web-prod-api-1` (EC2 instance)

<Steps>
  <Step title="Check existing tags">
    None found
  </Step>
  <Step title="Apply inference">
    Pattern "-prod-" matches → `environment: prod`
  </Step>
  <Step title="Apply defaults">
    owner absent → `owner: platform@company.com`

    (environment present, skip)
  </Step>
</Steps>

**Final tags:**
- `environment: prod` (inferred)
- `owner: platform@company.com` (default)

## Debugging Rules

### Preview Changes

Always use `tagctl plan` to preview before applying:

```bash
tagctl plan --output json | jq '.changes[] | {
  resource: .resource.name,
  tag: .tag,
  value: .new_value,
  reason: .reason
}'
```

### Check Specific Resources

```bash
tagctl plan | grep "web-prod"
```

### Verbose Scanning

```bash
tagctl scan --verbose
```

## Best Practices

<AccordionGroup>
  <Accordion title="Inference rules">
    - Be specific with patterns—use anchors (`^`, `$`)
    - Order matters—put specific patterns first
    - Test with `tagctl plan` before applying
    - Document naming conventions for your team
  </Accordion>

  <Accordion title="Rename rules">
    - Resolve conflicts by hand; tagctl never picks one of two values
    - Forbid the old key in `policy.forbidden` so it does not come back
    - Run `tagctl apply --allow-removals` with a role deployed with `AllowTagRemoval=true`, or the old keys stay
  </Accordion>

  <Accordion title="Inheritance rules">
    - Name the relation with `from` when a resource type has more than one parent
    - Fix the parents first: a child only inherits values that pass the policy
    - Rescan before planning so the recorded parents are current
  </Accordion>

  <Accordion title="Default rules">
    - Use sparingly—defaults indicate missing governance
    - Add review flags to mark resources for follow-up
    - Be conservative—generic defaults may be wrong
  </Accordion>
</AccordionGroup>
