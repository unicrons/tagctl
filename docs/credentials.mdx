## AWS Authentication

tagctl never reads credentials from `tagctl.yaml`. It uses the AWS SDK default
chain, the same one the AWS CLI and Prowler use, and each account entry only
says **which** identity to pick and, optionally, **which role** to assume with it.

<Steps>
  <Step title="SDK default chain">
    In order: `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`
    from the environment, `AWS_PROFILE`, the `default` profile in
    `~/.aws/config` / `~/.aws/credentials` (SSO and `credential_process`
    included), a web identity token, then the container or instance role.
  </Step>
  <Step title="Profile">
    `profile: name` (or `--profile`/`-p`) selects a shared config profile. An
    explicit profile takes precedence over exported keys, as in the AWS CLI.
  </Step>
  <Step title="Assume role">
    `role_arn` (or `--role`) calls `sts:AssumeRole` with whatever the previous
    steps resolved and uses the temporary credentials for every call. They are
    refreshed automatically before they expire.
  </Step>
</Steps>

<Note>
A config that still contains `access_key_id` / `secret_access_key` is rejected
by every command with a message pointing to `~/.aws/credentials` or the
environment.
</Note>

### Using Profiles (Recommended)

```yaml
clouds:
  aws:
    - profile: production
      regions: [us-east-1, eu-west-1]
    - profile: staging
      regions: [us-east-1]
```

Configure with AWS CLI:

```bash
aws configure --profile production
```

`tagctl scan --profile production` does the same without editing the file; the
flag applies to a config with zero or one AWS entry.

### Using SSO

```bash
# Login first
aws sso login --profile sso-prod
```

```yaml
clouds:
  aws:
    - profile: sso-prod
      regions: [us-east-1]
```

If your SSO tooling exports temporary credentials into the shell instead, omit
`profile`: the chain picks them up.

### Assuming Roles

One base credential, one entry per account:

```yaml
clouds:
  aws:
    - profile: audit-base
      role_arn: arn:aws:iam::111111111111:role/TagctlScan
      external_id: 4f2c9a
    - profile: audit-base
      role_arn: arn:aws:iam::222222222222:role/TagctlScan
      external_id: 4f2c9a
      session_duration: 7200
```

<ParamField path="role_arn" type="string">
  IAM role to assume. Required for the other fields.
</ParamField>
<ParamField path="external_id" type="string">
  Sent as `ExternalId` when the role's trust policy requires one.
</ParamField>
<ParamField path="session_duration" type="int" default="3600">
  Seconds the assumed session lasts, 900 to 43200. The role's own maximum applies.
</ParamField>
<ParamField path="role_session_name" type="string" default="tagctl">
  Session name recorded in CloudTrail.
</ParamField>
<ParamField path="mfa_serial" type="string">
  MFA device ARN when the trust policy demands MFA. tagctl prompts on stderr
  for the TOTP code before the first call. From a terminal the code is read
  without echo; when stdin is a pipe, tagctl reads one line from it.
</ParamField>

The same options exist as flags on `scan`, `apply` and `cost`: `--role`,
`--external-id`, `--session-duration`, `--role-session-name`, `--mfa-serial`.
A role configured in `~/.aws/config` (`role_arn` + `source_profile`) also
works through `profile:` alone, since the SDK resolves it.

The base identity needs `sts:AssumeRole` on the target role; the role carries
the tagctl policies (see [Scan role vs apply role](#scan-role-vs-apply-role)).

### Using Environment Variables

```bash
export AWS_ACCESS_KEY_ID=AKIA...
export AWS_SECRET_ACCESS_KEY=...
export AWS_SESSION_TOKEN=...   # temporary (SSO/STS) credentials
```

```yaml
clouds:
  aws:
    - regions: [us-east-1]  # No profile: the chain resolves the identity
```

Only one entry may rely on the chain without `profile` or `role_arn`, since it
identifies a single account.

### Using Instance Profile

When running on AWS infrastructure, no configuration needed:

```yaml
clouds:
  aws:
    - regions: [us-east-1, eu-west-1]
```

### Regions

The regions to **scan** always come from `regions` in `tagctl.yaml` or
`--region` (empty means every enabled region). The region of the profile or
`AWS_REGION` is only used for the initial STS and `DescribeRegions` calls; when
neither is set tagctl uses the first configured region, then `us-east-1`.

### Scan role vs apply role

Reading tags and writing them are different risks, so tagctl ships two roles
as CloudFormation templates in
[`permissions/aws/`](https://github.com/unicrons/tagctl/tree/main/permissions/aws):

| | `TagctlScan` | `TagctlApply` |
|---|---|---|
| Policies | `TagctlScan`, read-only | `TagctlScan` + `TagctlApply`, which adds the tag write actions scoped to the resource types tagctl tags |
| Commands | `scan`, `plan`, `diff`, `normalize`, `terraform`, `cost` | `apply` |
| Trust it to | a schedule, CI, an auditor | a person or a remediation pipeline, with MFA or an external id |
| Template | `tagctl-scan-role.yaml` | `tagctl-apply-role.yaml` |

Deploy them per account with `aws cloudformation deploy --capabilities
CAPABILITY_NAMED_IAM` (the commands are on the
[AWS provider page](/providers/aws#required-iam-permissions)). Point the
configuration file at the scan role and keep the apply role for the run that
remediates:

```yaml
clouds:
  aws:
    - profile: tooling
      role_arn: arn:aws:iam::111111111111:role/TagctlScan
```

```bash
tagctl scan
tagctl plan
tagctl apply --role arn:aws:iam::111111111111:role/TagctlApply \
             --mfa-serial arn:aws:iam::222222222222:mfa/me
```

`--role` replaces `role_arn` for that run (the file must have at most one AWS
entry), so the configuration never grants write access. The policy documents
change with every release and are maintained in one place, the
[AWS provider page](/providers/aws#required-iam-permissions).
`tag:GetResources` is the one action worth calling out: without it most
services are skipped rather than reported as untagged. `ce:GetCostAndUsage`
in the scan role only serves `tagctl cost`.

Both templates take an optional `OrgId` that adds `aws:PrincipalOrgID` to the
trust policy. The apply template keeps CodeBuild tagging off unless
`AllowCodeBuildTagging=true`, because `codebuild:UpdateProject` can also
rewrite a project's buildspec, and `ProtectedTagKeys` denies writes to the tag
keys your access policies depend on.

## Kubernetes Authentication

<Note>
The Kubernetes provider is experimental and not wired into the CLI yet (see
[provider status](/development#provider-status)). These are the settings it
reads through the official client-go library.
</Note>

### Using Kubeconfig (Default)

```yaml
clouds:
  kubernetes:
    - name: prod-cluster
      # Uses ~/.kube/config by default
```

### Using Specific Context

```yaml
clouds:
  kubernetes:
    - name: prod
      kubeconfig: ~/.kube/config
      context: prod-context

    - name: staging
      kubeconfig: ~/.kube/config
      context: staging-context
```

### In-Cluster (Running in Kubernetes)

```yaml
clouds:
  kubernetes:
    - name: current-cluster
      kubeconfig: in-cluster
      namespaces: [app, backend]
```

### Required RBAC Permissions

<Tabs>
  <Tab title="Read-Only (Scan)">
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: tagctl-reader
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "namespaces", "configmaps"]
    verbs: ["get", "list"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list"]
```
  </Tab>
  <Tab title="Read-Write (Apply)">
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: tagctl-writer
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "namespaces", "configmaps"]
    verbs: ["get", "list", "patch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch"]
```
  </Tab>
</Tabs>

Secrets are opt-in: grant them only when `resource_types` lists `k8s_secret`
(see [Kubernetes Provider](/providers/kubernetes#secrets-opt-in)).

### ClusterRoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: tagctl-binding
subjects:
  - kind: ServiceAccount
    name: tagctl
    namespace: default
roleRef:
  kind: ClusterRole
  name: tagctl-writer
  apiGroup: rbac.authorization.k8s.io
```

## Security Best Practices

<CardGroup cols={2}>
  <Card title="Never commit credentials" icon="ban">
    Use environment variables or profiles
  </Card>
  <Card title="Use least privilege" icon="shield">
    Only grant permissions needed
  </Card>
  <Card title="Rotate credentials" icon="arrows-rotate">
    Change keys regularly
  </Card>
  <Card title="Use IAM roles" icon="user-shield">
    Prefer roles over access keys
  </Card>
</CardGroup>

## Troubleshooting

<AccordionGroup>
  <Accordion title="AWS: Access Denied">
    Verify credentials:
    ```bash
    aws sts get-caller-identity --profile your-profile
    ```
  </Accordion>

  <Accordion title="AWS: No resources found">
    Check the region has resources:
    ```bash
    aws ec2 describe-instances --region us-east-1
    ```
  </Accordion>

  <Accordion title="Kubernetes: Connection refused">
    Check cluster connectivity:
    ```bash
    kubectl cluster-info
    kubectl config current-context
    ```
  </Accordion>

  <Accordion title="Kubernetes: Forbidden">
    Check RBAC permissions:
    ```bash
    kubectl auth can-i list pods --all-namespaces
    kubectl auth can-i patch deployments -n my-namespace
    ```
  </Accordion>
</AccordionGroup>

## Complete Example

```yaml
clouds:
  aws:
    # Production: uses SSO
    - profile: sso-production
      regions: [us-east-1, us-west-2]

    # Staging: uses regular profile
    - profile: staging
      regions: [us-east-1]

  # Kubernetes: accepted, not scanned yet
  # kubernetes:
  #   - name: prod-eks
  #     context: arn:aws:eks:us-east-1:123456789012:cluster/prod
  #     namespaces: []

policy:
  required:
    - name: environment
      values: [dev, staging, prod]
    - name: owner
      pattern: "^.+@company\\.com$"
```
