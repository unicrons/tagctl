`tagctl scan`, `plan` and `apply` work against every cluster listed under `clouds.kubernetes`.
Labels are the tags: tagctl reads `metadata.labels` and `apply` writes them with a merge patch.

## Resource Types

| Resource | Type | Scanned by default |
|----------|------|--------------------|
| Pod | `k8s_pod` | Yes (pods in phase `Succeeded` or `Failed` are skipped) |
| Deployment | `k8s_deployment` | Yes |
| Service | `k8s_service` | Yes |
| Namespace | `k8s_namespace` | Yes |
| ConfigMap | `k8s_configmap` | Yes |
| Secret | `k8s_secret` | No, opt-in |

Secrets are scanned only when `k8s_secret` is listed in `resource_types`. tagctl reads them through
the metadata API (`PartialObjectMetadata`), so secret data is never downloaded, and service account
tokens are excluded with the field selector `type!=kubernetes.io/service-account-token`. Every list
call is paginated (`limit` 500 with `continue` tokens).

In reports, the **account** of a resource is the cluster `name` from the config and its **region**
is the namespace (empty for namespaces themselves). Its ID is `<type>/<namespace>/<name>`.

## Limits

<Warning>
  **A label value cannot hold an e-mail address.** Kubernetes accepts at most 63 characters from
  `[A-Za-z0-9._-]`, starting and ending with a letter or digit. A policy such as
  `owner` with `pattern: "^.+@.+$"` can never be satisfied by a label: `scan` keeps reporting the
  tag as missing or invalid, and `apply` refuses the change. Annotations, which accept such values,
  are not read or written by tagctl.
</Warning>

- **Label syntax is checked before the API call.** `apply` fails every change of a resource whose
  plan holds an invalid label key or value, names the label in the error and sends nothing for that
  resource. The other resources in the plan are still applied and the command exits `2`. `plan` does
  not check label syntax, so a `rules.defaults` value such as `owner: platform@company.com` shows
  up in the plan and fails at `apply`.
- **Use a policy that labels can satisfy.** When the same policy also covers AWS with e-mail
  owners, keep the clusters in a config file of their own (`--config`) with a pattern such as
  `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$` for `owner`.
- **Only the six types above.** StatefulSets, DaemonSets, Jobs, CronJobs, Ingresses, PVCs and
  custom resources are not scanned.
- **Only the object's own `metadata.labels`.** Labelling a Deployment does not change its pod
  template, so its pods keep their labels; a pod labelled directly loses the label when it is
  recreated. Fix pod labels in the workload manifest.
- **`apply` patches live objects.** A GitOps controller or the next `helm upgrade` can revert a
  label that is not in the source manifest. Treat `apply` as a stopgap and the plan as the list of
  changes to make at the source.
- **Labels are removed only with `apply --allow-removals`.** `policy.forbidden` and `rules.rename`
  work on labels like on tags. The removal is a merge patch that sets the label to `null`, so it needs
  the same `patch` verb as adding one. Without the flag a rename adds the new label and keeps the old
  one. See [Removing Tags](/rules#removing-tags).
- **`rules.inherit` has no Kubernetes relation.** A pod does not inherit from its Deployment or
  namespace; the [relations](/rules#inheritance-rules) are all AWS ones.
- **`--region` is AWS-only.** Filter a cluster with `namespaces` and `resource_types`.
- **`tagctl cost` is AWS-only.**

## Configuration

```yaml
clouds:
  kubernetes:
    - name: production
      kubeconfig: ~/.kube/config
      context: prod-context
      # namespaces omitted: the whole cluster

    - name: staging
      context: staging-context
      namespaces:
        - app
        - backend

policy:
  required:
    - name: app
    - name: environment
      values: [dev, staging, prod]
    - name: owner
      pattern: "^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$"   # a team name, not an e-mail

rules:
  defaults:
    - resource: "k8s_*"
      when:
        "tag:owner": absent
      set:
        owner: platform-team
```

```bash
tagctl scan     # list and evaluate both clusters
tagctl plan     # propose labels from rules.infer and rules.defaults
tagctl apply    # patch the labels
```

### Configuration Options

<ParamField path="name" type="string" required>
  Identifies the cluster in reports, plans and resource identities. Must be unique: two clusters
  with the same name are rejected.
</ParamField>

<ParamField path="kubeconfig" type="string">
  Path to a kubeconfig file (`~/` is expanded), or `in-cluster` to use the pod's service account.
  When omitted, tagctl follows the kubectl loading rules: the files in `KUBECONFIG`, then
  `~/.kube/config`, then the in-cluster service account.
</ParamField>

<ParamField path="context" type="string">
  Kubeconfig context to use. Defaults to the current context.
</ParamField>

<ParamField path="namespaces" type="string[]">
  Namespaces to scan. Empty means the whole cluster: each resource type is listed once across all
  namespaces, which needs a ClusterRole. With a list, every call is scoped to one namespace and a
  namespace that does not exist is an error.
</ParamField>

<ParamField path="resource_types" type="string[]">
  Resource types to scan, from the table above. Defaults to every type except `k8s_secret`.
  `tagctl validate` rejects an unknown or repeated type.
</ParamField>

## Errors and Partial Scans

A kubeconfig that cannot be loaded, or a `context` that does not exist, stops the command before
anything is scanned. A cluster that cannot be reached, or a list call the credentials are not
allowed to make, makes the scan [partial](/commands#partial-scans): the resources that could be
read are kept, the scan JSON records `partial: true` with one error per failing call (prefixed
`cluster <name>:`), and `scan` exits `2` unless `--allow-partial` is set. An unreachable cluster is
never reported as zero resources. Each API request times out after 60 seconds.

## Authentication

### Using Kubeconfig (Default)

```yaml
clouds:
  kubernetes:
    - name: my-cluster
```

### Using Specific Context

```yaml
clouds:
  kubernetes:
    - name: prod
      kubeconfig: ~/.kube/config
      context: prod-eks-cluster

    - name: staging
      kubeconfig: ~/.kube/config
      context: staging-gke-cluster
```

### In-Cluster (Running in Kubernetes)

When tagctl runs as a pod:

```yaml
clouds:
  kubernetes:
    - name: current-cluster
      kubeconfig: in-cluster
      namespaces: [app, backend]
```

### EKS Authentication

```yaml
# ~/.kube/config
users:
- name: eks-user
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: aws
      args:
        - eks
        - get-token
        - --cluster-name
        - my-cluster
```

### GKE Authentication

```yaml
# ~/.kube/config
users:
- name: gke-user
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: gke-gcloud-auth-plugin
```

## Required RBAC Permissions

### Read-Only (Scan)

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: tagctl-reader
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "namespaces", "configmaps"]
    verbs: ["get", "list"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list"]
```

### Secrets (Opt-In)

Grant this only when `resource_types` lists `k8s_secret`. Kubernetes RBAC cannot restrict `list` to
metadata: the role allows reading secret data even though tagctl requests metadata only.

```yaml
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: ["list"]           # add "patch" for apply
```

### Read-Write (Apply)

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: tagctl-writer
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "namespaces", "configmaps"]
    verbs: ["get", "list", "patch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "patch"]
```

### ClusterRoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: tagctl-binding
subjects:
  - kind: ServiceAccount
    name: tagctl
    namespace: tagctl-system
roleRef:
  kind: ClusterRole
  name: tagctl-reader          # tagctl-writer to run apply
  apiGroup: rbac.authorization.k8s.io
```

<Tip>
  For namespace-scoped access, list the namespaces in `namespaces` and bind the same rules with a
  `Role` and `RoleBinding` in each one. tagctl then makes no cluster-wide call: it lists inside each
  namespace and reads the namespace object with `get`.
</Tip>

## Running tagctl in Kubernetes

No container image is published. Build a static binary from source, copy it into an image of your
own and push that image to a registry the cluster can pull from:

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o tagctl ./cmd/tagctl
```

### CronJob

`scan` runs once and exits, so schedule it instead of keeping it in a Deployment:

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: tagctl
  namespace: tagctl-system
spec:
  schedule: "0 6 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          serviceAccountName: tagctl
          restartPolicy: Never
          containers:
            - name: tagctl
              image: registry.example.com/tagctl:dev   # the image you built
              command: ["tagctl", "scan", "--config", "/etc/tagctl/tagctl.yaml", "--output", "json"]
              workingDir: /tmp                          # scan writes its reports to ./output
              volumeMounts:
                - name: config
                  mountPath: /etc/tagctl
          volumes:
            - name: config
              configMap:
                name: tagctl-config
```

### ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: tagctl-config
  namespace: tagctl-system
data:
  tagctl.yaml: |
    clouds:
      kubernetes:
        - name: current-cluster
          kubeconfig: in-cluster

    policy:
      required:
        - name: app
        - name: environment
          values: [dev, staging, prod]
```

### ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: tagctl
  namespace: tagctl-system
```

## Multi-Cluster Setup

One provider is built per entry, and a plan entry is only ever applied to the cluster it was
scanned from.

```yaml
clouds:
  kubernetes:
    # Production EKS
    - name: prod-eks
      kubeconfig: ~/.kube/config
      context: arn:aws:eks:us-east-1:123456789012:cluster/prod

    # Staging GKE
    - name: staging-gke
      kubeconfig: ~/.kube/config
      context: gke_my-project_us-central1_staging
      namespaces: [app, api]

    # Local development
    - name: minikube
      context: minikube
      namespaces: [default]
```

## Filtering Resources

### By Namespace

```yaml
clouds:
  kubernetes:
    - name: prod
      namespaces:
        - app
        - backend
        - frontend
      # Excludes: kube-system, kube-public, etc.
```

### By Resource Type

```yaml
clouds:
  kubernetes:
    - name: prod
      resource_types:
        - k8s_deployment
        - k8s_service
      # Only scan deployments and services
```

To scan secrets as well, list every type you want, `k8s_secret` included:

```yaml
clouds:
  kubernetes:
    - name: prod
      resource_types: [k8s_deployment, k8s_service, k8s_secret]
```

### By Policy

`ignore.resources` takes globs on the resource type, for example `k8s_configmap` or `k8s_*`.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Connection refused">
    The scan is partial and names the cluster. Check cluster connectivity:
    ```bash
    kubectl cluster-info
    kubectl config current-context
    ```
  </Accordion>

  <Accordion title="Forbidden errors">
    Check RBAC permissions:
    ```bash
    kubectl auth can-i list pods --all-namespaces
    kubectl auth can-i patch deployments -n my-namespace
    ```
  </Accordion>

  <Accordion title="Context not found">
    List available contexts:
    ```bash
    kubectl config get-contexts
    ```
    Use the exact context name in your config.
  </Accordion>

  <Accordion title="apply: not a valid Kubernetes label value">
    The plan holds a value labels cannot store, usually an e-mail address from `rules.defaults`.
    Change the rule to a value made of letters, digits, `-`, `_` and `.` (63 characters at most),
    then run `tagctl plan` again. See [Limits](#limits).
  </Accordion>

  <Accordion title="In-cluster config fails">
    Ensure the pod has a ServiceAccount with proper RBAC:
    ```bash
    kubectl get serviceaccount tagctl -n tagctl-system
    kubectl get clusterrolebinding tagctl-binding
    ```
  </Accordion>
</AccordionGroup>
