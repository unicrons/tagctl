## Supported Resources

tagctl discovers **106 resource types** across the same AWS services Prowler audits. Every type is listed by a dedicated
service API, so untagged resources are found too. Tags
are then read in bulk through the Resource Groups Tagging API (see
[How tags are read](#how-tags-are-read)); the **Write API** column is what
`tagctl apply` calls.

## How tags are read

Discovery and tag reading are two different steps:

1. **Discovery** always uses each service's own List/Describe API, so a
   resource that has never been tagged is still found.
2. **Tags** come from a `tag:GetResources` sweep per region, started before
   discovery and shared by every lister. The sweep is filtered to the resource
   types tagctl audits and split into twelve parallel paginators, so an
   account with tens of thousands of tagged resources still reads in a few
   seconds. A discovered ARN missing from the sweep is untagged. Services
   whose Describe call already returns tags inline never need it: EC2, Auto
   Scaling, ECS, EKS, EFS, RDS clusters and snapshots, MSK, Redshift, Secrets
   Manager, CloudFormation, FSx, API Gateway, Access Analyzer,
   Amplify, AppSync, Batch, Direct Connect, DLM, DRS, GuardDuty, Lightsail,
   Data Pipeline and SSM documents. ALB/NLB load balancers and Global
   Accelerator always read tags through their own API
   (`elasticloadbalancing:DescribeTags`, `globalaccelerator:ListTagsForResource`).

When `tag:GetResources` is denied or fails, tagctl degrades in two ways:

- Services with a per-resource tag API (RDS instances, Lambda, SNS, SQS, S3,
  DynamoDB, ElastiCache, ECR, KMS, Kinesis, CloudWatch Logs, classic load
  balancers, target groups and CloudTrail) fall back to it, one call per
  resource.
- Services with no usable tag API of their own are **skipped** with an
  `[ERROR]` line naming the service and region, and are never reported as
  untagged: ACM, ACM PCA, AppStream, Athena, Backup, Bedrock, CloudFront,
  CloudWatch alarms, CodeArtifact, CodeBuild, CodeCommit, CodePipeline,
  Cognito, Config,
  DataSync, Directory Service, DMS, Elastic Beanstalk, EMR, EventBridge,
  Firehose, Firewall Manager, Glacier, Glue, IAM, MemoryDB, MQ, Network
  Firewall, OpenSearch, Roles Anywhere, Route 53, SageMaker, SES, Service
  Catalog, Shield, SSM parameters, Incident Manager, Step Functions, Storage
  Gateway, Transfer Family, WAF, Well-Architected and WorkSpaces.

A resource whose own tag call fails (access denied, network timeout) is
skipped the same way, never reported as untagged. A resource deleted between
listing and the tag read is simply dropped (visible at `--log-level debug`)
and not counted. Discovery then returns an
error that counts the skipped resources and services per service and, like
every lister error, names the account (and region) it comes from, so
`tagctl scan` reports the scan as completed with errors instead of success.

Global services (Route 53, CloudFront, IAM, Shield, WAF Classic for
CloudFront, WAFv2 CloudFront scope) are listed once per account and read their
tags from the `us-east-1` sweep, which tagctl runs even when `us-east-1` is
not in `regions`. Global Accelerator only exists in `us-west-2` and reads and
writes its tags through its own API.

Some services report "not set up" instead of an empty list: DRS in a region
never initialised, Shield without an Advanced subscription, Firewall Manager
outside the administrator account. tagctl treats those answers as zero
resources (visible at `--log-level debug`), not as errors. Lightsail is only
called in the regions where it has an endpoint.

<Warning>
`tag:GetResources` is eventually consistent. Tags written by `tagctl apply`
can take a few minutes to appear in the next `scan`; the per-resource
fallback APIs are read-after-write.
</Warning>

## Configuration

```yaml
clouds:
  aws:
    # Scan all available regions (auto-discovery)
    - profile: production

    # Or specify specific regions
    - profile: staging
      regions:
        - us-east-1
        - eu-west-1
```

### Configuration Options

<ParamField path="profile" type="string">
  AWS CLI profile name from `~/.aws/credentials` or `~/.aws/config`.
</ParamField>

<ParamField path="role_arn" type="string">
  IAM role to assume with the resolved credentials; `external_id`,
  `session_duration`, `role_session_name` and `mfa_serial` refine it.
</ParamField>

<ParamField path="regions" type="string[]">
  List of AWS regions to scan. **If omitted, all available regions are automatically discovered and scanned.** The list also filters S3: buckets located outside it are not read.
</ParamField>

## Region Selection

tagctl supports flexible region configuration:

### Auto-Discovery (Default)

When no regions are specified, tagctl automatically discovers all available regions:

```yaml
clouds:
  aws:
    - profile: production  # Scans all 17+ AWS regions
```

### Specific Regions in Config

```yaml
clouds:
  aws:
    - profile: production
      regions: [us-east-1, eu-west-1]
```

### Command-Line Override

The `--region` flag overrides the config file:

```bash
# Scan only eu-west-1, regardless of config
tagctl scan --region eu-west-1

# Scan multiple specific regions
tagctl scan --region eu-west-1 --region us-east-1
```

## Authentication

Credentials come from the AWS SDK default chain (environment, `~/.aws`
profiles and SSO, web identity, container or instance role). An account entry
selects a `profile` and can assume a `role_arn` on top; keys are never read from
`tagctl.yaml`. `--profile` and `--role` (with `--external-id`,
`--session-duration`, `--role-session-name`, `--mfa-serial`) do the same from
the command line. The full reference lives on the
[Credentials page](/credentials#aws-authentication).

The regions to scan always come from `regions` or `--region`; the profile's
region only serves the initial STS call.

## Required IAM Permissions

tagctl needs two levels of access and ships one role for each, as
CloudFormation templates under
[`permissions/aws/`](https://github.com/unicrons/tagctl/tree/main/permissions/aws):

| Role | Policies | Commands | Hand it to |
|------|----------|----------|------------|
| `TagctlScan` | `TagctlScan` | `scan`, `plan`, `diff`, `normalize`, `terraform`, `cost` | Scheduled jobs, CI, auditors. It cannot write a tag. |
| `TagctlApply` | `TagctlScan` + `TagctlApply`, plus `TagctlApplyCodeBuild` and `TagctlProtectedTagKeys` when enabled | `apply` | People and pipelines that remediate, behind MFA or an external id. |

The apply policy is additive: it holds only the tag write actions and always
sits next to the scan policy, which is where `sts:GetCallerIdentity`, the
discovery calls and the S3 `Get*` reads that precede `PutBucketTagging` come
from. Deploy the role in every account tagctl will touch:

```bash
aws cloudformation deploy \
  --template-file permissions/aws/tagctl-scan-role.yaml \
  --stack-name tagctl-scan-role \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides TrustedPrincipalArn=arn:aws:iam::111111111111:root
```

`TrustedPrincipalArn` is who may assume the role: an account root, a role or
an Identity Center permission set. `ExternalId`, `RequireMFA` (default `true`
on the apply template), `OrgId`, `MaxSessionDuration` and
`PermissionsBoundaryArn` are optional. `OrgId` adds `aws:PrincipalOrgID` to the
trust policy, so the caller must also belong to that organization. The apply
template adds `AllowCodeBuildTagging` and `ProtectedTagKeys`, described below.
The `TagctlConfig` output is the entry to paste under `clouds.aws`; the base
identity only needs `sts:AssumeRole` on the role. For many accounts, deploy the
same template as a StackSet.

The policy documents are also available on their own as
`tagctl-scan-policy.json`, `tagctl-apply-policy.json` and
`tagctl-apply-codebuild-policy.json`, for Terraform or a role you already have.
Every copy on this page is checked against those files by
`go test ./internal/provider/aws/`.

<Note>
  This policy only adds the write actions: attach it together with the scan
  policy, as the `TagctlApply` role does. `PutBucketTagging` replaces the whole
  tag set, so tagctl reads the existing tags first through the scan policy's
  `s3:GetBucketTagging`. `tag:TagResources` delegates to each service, so the
  service's own tagging action must be allowed as well; a resource the service
  rejects is reported as a failed change with the service's error code, the
  rest of the batch still applies.
</Note>

Each service action only reaches the ARNs of the resource types tagctl tags,
as the
[Service Authorization Reference](https://docs.aws.amazon.com/service-authorization/latest/reference/reference_policies_actions-resources-contextkeys.html)
lists them: `ec2:CreateTags` cannot tag a transit gateway. The reference maps
API Gateway tagging (REST and HTTP/WebSocket APIs) to `apigateway:PUT`, `POST`
and `PATCH`; the policy grants `PUT` and `POST` on `/tags/*` only, so they
cannot create, update or import an API. `tag:TagResources` and
`workspaces:CreateTags` stay on `"*"` because the reference lists no resource
type for them. The ARNs use the `aws` partition; in AWS China or GovCloud
replace `arn:aws:` with `arn:aws-cn:` or `arn:aws-us-gov:`.

<Note>
  Service Catalog portfolios are discovered, but tagging them may fail. The
  Resource Groups
  [supported resources](https://docs.aws.amazon.com/ARG/latest/userguide/supported-resources.html)
  table marks `AWS::ServiceCatalog::Portfolio` as not taggable through Tag
  Editor. The reference maps `servicecatalog:TagResource` only to AppRegistry
  applications and attribute groups, which tagctl never tags, so the policy
  does not grant it. Portfolio tags change through
  `servicecatalog:UpdatePortfolio`, which tagctl neither calls nor grants. The
  reference does not say which action `tag:TagResources` checks for a
  portfolio.
</Note>

### CodeBuild Tagging (Opt-In)

CodeBuild has no tag-only IAM action: project tags are written through
`codebuild:UpdateProject`, which can also replace a project's buildspec and
service role. It is not part of the apply policy, so by default `tagctl apply`
reports CodeBuild changes as failed and applies the rest. Deploy the apply
template with `AllowCodeBuildTagging=true`, or attach this policy yourself:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CodeBuildTagging",
      "Effect": "Allow",
      "Action": [
        "codebuild:UpdateProject"
      ],
      "Resource": [
        "arn:aws:codebuild:*:*:project/*"
      ]
    }
  ]
}
```

### Protected Tag Keys

`ProtectedTagKeys` on the apply template attaches `TagctlProtectedTagKeys`, a
Deny on any request whose `aws:TagKeys` match one of the comma-separated keys
(`ForAnyValue:StringLike`, wildcards allowed, no spaces around the commas).
Use it for the keys your ABAC policies check, so the apply role cannot grant
itself or anyone else access by rewriting them:

```bash
aws cloudformation deploy \
  --template-file permissions/aws/tagctl-apply-role.yaml \
  --stack-name tagctl-apply-role \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
    TrustedPrincipalArn=arn:aws:iam::222222222222:role/platform-admin \
    ProtectedTagKeys=access-team,access-level
```

<Warning>
  The deny only applies to actions whose Service Authorization Reference entry
  lists `aws:TagKeys`. `s3:PutBucketTagging`, `route53:ChangeTagsForResource`
  and `glacier:AddTagsToVault` do not, so S3 bucket, Route 53 hosted zone and
  Glacier vault tags stay writable. `StringLike` is case-sensitive, but tag
  keys on IAM users and roles are not: `iam:TagRole` with `Access-Team`
  overwrites `access-team` without matching `ProtectedTagKeys=access-team`.
  List the case variants, or use `?` for letters whose case may vary
  (`?ccess-?eam`). IAM caps the inline policies of a role at
  10,240 characters in total, whitespace excluded; the apply role leaves about
  900 for the key list.
</Warning>

## Multi-Account Setup

### Using AWS Organizations

```yaml
clouds:
  aws:
    # Production account
    - profile: org-production
      regions: [us-east-1, eu-west-1]

    # Staging account
    - profile: org-staging
      regions: [us-east-1]

    # Development account
    - profile: org-development
      regions: [us-east-1]
```

### Using Cross-Account Roles

Deploy `tagctl-scan-role.yaml` in every member account (a StackSet does it
once) with the tooling account as `TrustedPrincipalArn`, then either list the
accounts in `tagctl.yaml` with `role_arn` or configure the roles in
`~/.aws/config`:

```ini
[profile production]
role_arn = arn:aws:iam::111111111111:role/TagctlScan
source_profile = default

[profile staging]
role_arn = arn:aws:iam::222222222222:role/TagctlScan
source_profile = default
```

## Troubleshooting

Use debug logging to trace issues:

```bash
tagctl scan --log-level debug
```

<AccordionGroup>
  <Accordion title="Access Denied errors">
    Verify IAM permissions:
    ```bash
    aws sts get-caller-identity --profile your-profile
    aws ec2 describe-instances --profile your-profile --region us-east-1
    ```
  </Accordion>

  <Accordion title="Resources in the wrong region, or none at all">
    tagctl never takes the region from the profile or `AWS_REGION`: it scans
    exactly `regions` from `tagctl.yaml` (or `--region`), and discovers every
    region through `ec2:DescribeRegions` when the list is empty. The first
    configured region (or `us-east-1`) is also where the initial STS call goes.
  </Accordion>

  <Accordion title="No resources found in region">
    Check the region has resources:
    ```bash
    aws ec2 describe-instances --region us-east-1 --query 'Reservations[].Instances[].InstanceId'
    ```

    Use debug logging to see exactly what's being scanned:
    ```bash
    tagctl scan --log-level debug --region us-east-1
    ```
  </Accordion>

  <Accordion title="S3 buckets missing from the report">
    Buckets are listed once (S3 is global) and then filtered by the configured
    `regions`; a bucket in `us-west-2` is not reported when only `eu-west-1` is
    configured. Omit `regions` to scan every bucket.

    A bucket whose tags cannot be read (network timeout, access denied) is
    skipped with an `[ERROR]` line rather than reported as untagged, and
    counted in the error the scan ends with. Run with
    `--log-level debug` to see each bucket's region and the SDK retries.
  </Accordion>

  <Accordion title="A service is 'skipped' with a tag:GetResources error">
    The role can list the service but not read tags in bulk, and that service
    has no per-resource tag API tagctl can fall back to. Grant
    `tag:GetResources` (see [Read-Only](#read-only-scan)). Nothing from that
    service is reported until then; skipping is deliberate so a permission gap
    never shows up as untagged resources.
  </Accordion>

  <Accordion title="Tags applied a moment ago are still reported missing">
    `tag:GetResources` is eventually consistent; wait a few minutes and scan
    again. Run with `--log-level debug` and look for the
    `AWS Tagging: ... discovered resources have tags` line per region to
    check what the bulk sweep returned.
  </Accordion>

  <Accordion title="Rate limiting">
    Every (region × service) lister runs in its own goroutine and per-resource
    tag calls fan out with a fixed limit of 16 in flight; the SDK retries
    throttled calls with exponential backoff (visible at `--log-level debug`).
    The concurrency is not configurable.
  </Accordion>
</AccordionGroup>
