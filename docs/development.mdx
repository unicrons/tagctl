## Provider Status

| Provider | Status | Details |
|----------|--------|---------|
| **AWS** | Supported | 106 resource types, see [AWS provider](/providers/aws) |
| **Kubernetes** | Supported | Pods, deployments, services, namespaces, config maps and (opt-in) secrets; labels are the tags. Label values cannot hold e-mail addresses, annotations are not read, and no other resource type is scanned. See [Kubernetes provider](/providers/kubernetes) |
| **GCP** | Not started | `clouds.gcp` is a reserved config key with no provider behind it |
| **Azure** | Not started | `clouds.azure` is a reserved config key with no provider behind it |

`tagctl validate` counts a `gcp` or `azure` entry as a configured cloud, but
every other command scans and applies only `clouds.aws` and
`clouds.kubernetes`. A file with neither makes `scan` show demo data and
`apply` simulate its changes.

Contributions are welcome. See [Roadmap](/roadmap#providers) for what is left.

## Quick Start

```bash
# Clone the repository
git clone https://github.com/unicrons/tagctl.git
cd tagctl

# Install tools and enable pre-commit hooks
make setup

# Build and test
make build
make test

# Test with mock data
./bin/tagctl scan --mock
```

Building needs Go 1.26.6 or later, the version `go.mod` requires.

## Dev Container

`.devcontainer/devcontainer.json` opens the repository in VS Code Dev Containers
or GitHub Codespaces with:

| Component | Source |
|-----------|--------|
| Go 1.26 on Debian 13 (trixie) | `mcr.microsoft.com/devcontainers/go:2-1.26-trixie` |
| Node.js 22, for the Mintlify docs | `ghcr.io/devcontainers/features/node:2` |
| golangci-lint and trufflehog | `make tools`, run when the container is created |

The container does not run `make hooks`. With a local checkout the repository
is mounted from your machine, so `git config core.hooksPath` would also enable
the hook for commits made outside the container. Run `make hooks` yourself to
opt in.

To preview the docs in a container, install Docker with the Compose plugin,
then run this from the repository root:

```bash
docker compose up --build
```

Open [http://localhost:3000](http://localhost:3000). The Compose service mounts
`./docs` into the container, so edits to the docs appear in the preview. Stop
the service with `Ctrl+C`, or run `docker compose down` from another terminal.

For a direct local preview, install the Mintlify CLI at the version
`.github/workflows/ci.yml` pins:

```bash
npm install -g mint@4.2.313
cd docs && mint dev
```

The image sets `GOTOOLCHAIN=local`, so it never downloads a newer Go. When
`go.mod` moves to a new Go minor version, bump the image tag with it.

## Development Setup

### 1. Install Development Tools

```bash
make tools
```

This installs the versions CI pins into `$(go env GOPATH)/bin` (`GOBIN` when
set). The pre-commit hook, `make lint` and `make check-secrets` look there
before `PATH`, so an older copy elsewhere does not get in the way.

| Tool | Version | Purpose |
|------|---------|---------|
| **trufflehog** | v3.97.4 | Secret detection |
| **golangci-lint** | v2.13.2 | Go linter (14 linters enabled in `.golangci.yml`) |

To bump a tool, change `TRUFFLEHOG_VERSION` or `GOLANGCI_LINT_VERSION` in the
`Makefile` and the matching pin in `.github/workflows/ci.yml`.

### 2. Enable Pre-commit Hooks

```bash
make hooks
```

To disable:

```bash
make hooks-uninstall
```

## Pre-commit Checks

Every commit runs these checks automatically. The hook copies the index into
the git directory and runs them there, so it checks what is staged: an unstaged
fix does not rescue a commit and an unstaged mistake does not block it.

| Check | Tool | Description |
|-------|------|-------------|
| Secrets | trufflehog | Staged files; any finding fails, verified or not |
| Format | gofmt | Staged Go files |
| Lint | golangci-lint | Issues on staged lines against `HEAD` (the whole tree on a first commit; `go vet` when golangci-lint is not installed) |
| Build | go build | Compilation check |
| Tests | go test | Unit tests (`-short`) |

### Running Checks Manually

```bash
# All checks
make check

# Individual checks
make check-secrets
make check-fmt
make lint
make test
```

### Bypassing Checks

<Warning>
  Only use in emergencies. Skipping checks can introduce bugs or security issues.
</Warning>

```bash
git commit --no-verify
```

### Secret Detection

Trufflehog scans for:
- AWS credentials
- Private keys (RSA, DSA, EC, PGP)
- API tokens (GitHub, Slack)
- High-entropy strings

`make check-secrets` scans every file git would commit (tracked files plus
untracked ones `.gitignore` does not exclude); the pre-commit hook scans the
staged files. Any finding fails the check, verified or not.

To accept a false positive, add a regular expression matching its path to
`.trufflehog-ignore`, one per line (`#` starts a comment):

```text
^test/testdata/fake-credentials\.json$
```

## Data Flow

Each command passes data to the next via JSON files:

```bash
tagctl scan                              # → output/scan-TIMESTAMP.json
tagctl plan                              # Uses latest scan → output/plan-TIMESTAMP.json
tagctl plan --scan output/scan-*.json    # Use specific scan
tagctl apply                             # Uses latest plan
tagctl apply --plan output/plan-*.json   # Use specific plan
```

## Key Types

### Finding (PASS/FAILED)

The evaluator generates **Findings** for each resource+tag combination:

```go
type Finding struct {
    Resource Resource      `json:"resource"`
    Tag      string        `json:"tag"`
    Status   FindingStatus `json:"status"`   // "PASS" or "FAILED"
    Reason   ViolationReason `json:"reason"` // "compliant", "missing", "invalid_value"
    Expected string        `json:"expected,omitempty"`
    Actual   string        `json:"actual,omitempty"`
}
```

| Status | Reason | Meaning |
|--------|--------|---------|
| PASS | compliant | Tag present and valid |
| FAILED | missing | Required tag not present |
| FAILED | invalid_value | Value not in allowed list |
| FAILED | invalid_format | Value doesn't match pattern |

### Resource

```go
type Resource struct {
    ID          string            `json:"id"`
    ARN         string            `json:"arn,omitempty"` // Full AWS ARN
    Type        string            `json:"type"`     // e.g., "aws_instance"
    Name        string            `json:"name"`
    Region      string            `json:"region"`
    Account     string            `json:"account"`
    Provider    string            `json:"provider"` // "aws"
    Tags        map[string]string `json:"tags"`
    UnknownTags []string          `json:"unknown_tags,omitempty"` // Terraform: values known only after apply
    CreatedAt   *time.Time        `json:"created_at,omitempty"`
}
```

### Writing Tests

Use table-driven tests:

```go
func TestEvaluateResourceFindings(t *testing.T) {
    tests := []struct {
        name       string
        resource   types.Resource
        wantPass   int
        wantFailed int
    }{
        {
            name: "compliant resource",
            resource: types.Resource{
                Tags: map[string]string{"environment": "prod"},
            },
            wantPass:   1,
            wantFailed: 0,
        },
        {
            name: "missing tag",
            resource: types.Resource{
                Tags: map[string]string{},
            },
            wantPass:   0,
            wantFailed: 1,
        },
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            findings := evaluator.EvaluateResourceFindings(tt.resource)
            pass, failed := countFindings(findings)
            if pass != tt.wantPass || failed != tt.wantFailed {
                t.Errorf("got %d pass, %d failed; want %d, %d",
                    pass, failed, tt.wantPass, tt.wantFailed)
            }
        })
    }
}
```

### Testing without an AWS account

No part of the test suite needs cloud credentials, and a change can be
validated end to end without them. localstack, moto and other AWS emulators
are not part of the test setup: `compose.yaml` only serves the docs preview,
and CI runs `go test` with no AWS access at all.

**Run the CLI on demo data.** `scan --mock` evaluates a built-in set of
resources (`engine.NewMockScanner`) and writes the same reports a real scan
does, so `plan`, `diff`, `normalize` and the report formats can be exercised
on its output. `apply` simulates its changes when the config has no AWS
account.

```bash
make build
./bin/tagctl scan --mock --sarif /tmp/tagctl.sarif
./bin/tagctl plan
```

**Evaluate fixture resources.** `evaluate` reads resources from JSON instead
of the cloud, which covers policy and evaluator changes:

```bash
./bin/tagctl evaluate \
  --resources test/testdata/fixtures/resources-aws.json \
  --policy test/testdata/configs/valid.yaml
```

**Test a lister against a mock client.** Each AWS lister is split in two:
`list<Service>` resolves the real regional client and `list<Service>From`
takes a narrow interface holding only the SDK calls it makes. A test
implements that interface with a struct and passes it in.
`internal/provider/aws/efs.go` and `efs_test.go` are a complete example:

```go
// efs.go
type efsAPI interface {
    DescribeFileSystems(ctx context.Context, params *efs.DescribeFileSystemsInput, optFns ...func(*efs.Options)) (*efs.DescribeFileSystemsOutput, error)
    TagResource(ctx context.Context, params *efs.TagResourceInput, optFns ...func(*efs.Options)) (*efs.TagResourceOutput, error)
}

// efs_test.go
mock := &mockEFSClient{pages: [][]efstypes.FileSystemDescription{ /* ... */ }}
resources, err := testProvider().listEFSFileSystemsFrom(context.Background(), mock, "us-east-1")
```

`testProvider()` (`ec2_network_test.go`) builds a `Provider` with a fixed
account and no AWS session. Cover at least pagination, a list error and the
tag-read failure path of a new lister. `TestPermissionPolicies_*` then fails
if the lister calls an API the IAM policies in `permissions/aws/` do not allow.

**Use the shared fixtures.** `test/testdata/configs/` holds valid and invalid
`tagctl.yaml` files, `test/testdata/fixtures/` resources, scan results and
plans as JSON. Load them through `test/testutil` (`ConfigPath`, `FixturePath`,
`LoadResources`, `LoadScanResult`, `LoadPlan`) instead of building paths by
hand. `evaluate-violations.golden.json` pins the evaluator's output; a change
that moves it needs the golden file updated in the same commit.

What mocks cannot show is how a real service answers: throttling, eventual
consistency of the bulk tag API, or an IAM action missing from the policy. If
you could not check that, say so in the pull request so reviewers know the
change has not run against AWS.

## Releasing

A release is a tag. Pushing `vX.Y.Z` runs `.github/workflows/release.yml`,
where GoReleaser (`.goreleaser.yaml`) does the rest:

```bash
git switch main && git pull
git tag v0.1.0
git push origin v0.1.0
```

| Output | Where |
|--------|-------|
| `tagctl_<os>_<arch>.tar.gz` (`.zip` on Windows) for Linux, macOS and Windows on amd64 and arm64, plus `checksums.txt` | The GitHub Release, with notes grouped by commit type |
| Build provenance attestation for every archive | `gh attestation verify <archive> --repo unicrons/tagctl` |
| Multi-arch image (linux/amd64, linux/arm64) tagged `vX.Y.Z` and `latest` | `ghcr.io/unicrons/tagctl` |
| Homebrew cask | `unicrons/homebrew-tap`, once the tap is set up |

A tag with a pre-release suffix (`v0.2.0-rc.1`) is published as a GitHub
pre-release, does not move the image `latest` tag and is not sent to the tap.

The job runs in the `release` environment, which GitHub creates on the first
run. Add required reviewers to it in the repository settings to gate releases
behind an approval.

### One-time setup

The binaries and the image need nothing beyond the workflow. Two things do,
and only an organization owner can do them:

1. **Make the image public.** GitHub creates the `tagctl` container package
   as private on the first release. Open the package settings and change its
   visibility to public, otherwise `docker pull` needs a login.
2. **Create the Homebrew tap.** Until both steps below are done the release
   skips the tap and still succeeds; the cask is only written to `dist/`.
   - Create the public repository `unicrons/homebrew-tap` with an initial
     commit (GoReleaser pushes `Casks/tagctl.rb` to its default branch).
   - Create a fine-grained personal access token limited to that repository
     with **Contents: read and write**, and save it as the Actions secret
     `HOMEBREW_TAP_TOKEN` (repository secret, or a secret of the `release`
     environment). The next release publishes the cask.

### Checking a pipeline change

Nothing here publishes; the artifacts land in `dist/` and the images stay in
the local Docker daemon:

```bash
brew install goreleaser
goreleaser check
goreleaser release --snapshot --clean --skip=publish
./dist/tagctl_darwin_arm64_v8.0/tagctl version   # the directory of your platform
```

The root `Dockerfile` is the release image and only builds inside GoReleaser's
context, where the binaries are already compiled; `docker build .` on a plain
checkout fails on its `COPY`.

### Commit Messages

Follow conventional commits, `type(scope): summary`, subject of at most 60
characters. Release notes are generated from them.

```
feat(azure): add support for Azure resources
fix(engine): handle empty tag values correctly
docs(credentials): update credentials documentation
test(engine): add evaluator edge case tests
refactor(provider): simplify provider interface
chore(merge): take changes
```
